# UNIVERSE OF ME 高品质世界资产生产规范

状态：生产门槛草案，2026-11-01

这份规范定义环境资产进入 UNIVERSE OF ME 前必须满足的条件。它不是新的场景实现，也不把 Seacliff Beach 或现有 R1/R2 资产标记为合格生产资产。

## 1. 目标与边界

环境资产必须服务于真实的 Three.js/R3F 实时场景：用户可以旋转、移动、观察地形和水岸，并在稳定的资源预算内看到一致的材质、光照和空间构图。

Blender、Cycles 或离线渲染截图只能作为美术基准，不能替代浏览器验收。概念图、单机位渲染图和独立模型缩略图不能作为完整世界交付。

资产包必须明确区分：

- `source`：可编辑的 Blender 工程或等价 DCC 工程。
- `runtime`：经过验证的 glTF 2.0/GLB 文件、纹理、LOD 和碰撞代理。
- `evidence`：同机位 Blender 基准、Three.js 截图、漫游录像、性能数据和许可清单。

## 2. 可直接用于 Three.js 的资产要求

### 2.1 几何与场景组织

- 使用 glTF 2.0，优先 GLB 分区包；不得依赖 Blender 插件、Geometry Nodes、Cycles 节点或运行时生成器才能显示主体环境。
- 地形、海岸线、岩体、植被、水体和远景必须有清晰的节点命名与分区边界。单个场景包不得把整个星球压成一个不可剔除的网格。
- 每个可探索分区都必须提供可见几何、碰撞代理和加载边界。碰撞代理使用低面数网格，不用渲染网格直接承担碰撞。
- 植被和重复岩石使用可实例化的单元；实例来源必须有授权记录，不能依赖用户端可编辑的外部散布插件。
- 交付至少两级 LOD，建议 hero 资产三到四级。LOD 切换距离、屏幕误差或触发规则写入 manifest。
- 所有网格应用尺度和变换，法线方向正确，UV 不依赖 Blender 特有节点。坐标、单位、原点和地面高度写入场景说明。

### 2.2 材质与纹理

- 只使用 glTF PBR 可表达的材质：base color、metallic、roughness、normal、occlusion、emissive 和 alpha。
- Blender Principled 输入必须能映射到 glTF；Cycles 专用混合、程序噪声、体积、复杂节点组、对象信息驱动颜色不作为运行时依赖。
- 每个材质给出纹理色彩空间、通道打包方式、法线方向和 alpha 模式。透明材质数量要受控，树叶优先使用经过测试的 alpha mask 或双面材质。
- 纹理优先 KTX2/Basis 压缩；未压缩 PNG/JPEG 只用于源文件或确有必要的例外。纹理尺寸随 LOD 分级，不能把 4K 纹理无条件用于所有设备。
- 材质不能依赖离线反射探针才能成立。环境反射使用受控的实时 IBL 或低成本环境贴图，水面需要明确的实时近似方案。

### 2.3 天空、光照和水体

- 天空交付为可复现的实时方案：HDRI/环境贴图、程序天空或两者组合，并记录曝光、色彩空间和旋转。
- 主光源使用方向光或有限数量的实时光；阴影贴图分辨率、偏移和级联策略写入质量档位。
- 烘焙光照只用于静态区域，必须提供运行时可接受的替代，不能依靠 Cycles 体积雾或离线合成通道。
- 水体需有独立的可见网格、深浅色逻辑、法线动画和岸线过渡；不以透明平面加单色反射冒充海岸。
- 云层、雾和大气效果必须在低档位可关闭或降级，且不能遮挡碰撞和交互对象。

## 3. Blender 实时制作流程

1. 先做一块可探索的连续构图：明确观察入口、主焦点、路径、海岸线、遮挡关系和远景终点。先通过灰盒和相机草图确认空间关系。
2. 雕刻或建立连续地形，制作材质权重/遮罩。海岸、水面、沙滩和岩石接触边界必须由同一地形设计驱动。
3. 以 hero、中景、远景三层布置植被和岩石。重复资产需要旋转、尺度和密度变化，但不得由随机散布替代人工构图。
4. 为渲染网格制作碰撞代理、导航路径和 LOD。检查相机最低高度、斜坡、海岸边界和不可进入区域。
5. 用 Blender 的 glTF exporter 导出测试包，再在 glTF Inspector/Blender 和 Three.js 中逐项检查材质、法线、透明、纹理、节点层级和尺寸。
6. 用 KTX2/Basis、meshopt 或 Draco 做压缩，记录压缩前后大小、解码时间和视觉差异。压缩后必须重新截图，不以源文件渲染代替。
7. 在 Three.js 中用与 Blender 相同的机位、焦距、曝光和主光方向进行对照；先修正资产和烘焙，再调整运行时，不通过 Bloom 或颜色滤镜掩盖导出损失。

## 4. 可复用的开源工具

这些工具解决导出、压缩和运行时集成问题，不替代环境美术：

| 工具 | 用途 | 当前判断 |
| --- | --- | --- |
| [Khronos glTF-Blender-IO](https://github.com/KhronosGroup/glTF-Blender-IO) | Blender 到 glTF/GLB 导出 | 必需；必须用项目锁定的 Blender 版本回归 |
| [glTF Transform](https://github.com/donmccurdy/glTF-Transform) | 检查、变换、纹理压缩、拆分 | 推荐用于 CI 前的资产检查和 KTX2 管线 |
| [meshoptimizer/gltfpack](https://github.com/zeux/meshoptimizer) | meshopt 几何压缩、简化和量化 | 推荐；需要逐级 LOD 和视觉回归 |
| KTX-Software/BasisU | GPU 纹理压缩 | 推荐；按目标浏览器和设备测试 |
| R3F / Drei `useGLTF` | 场景加载、预加载和运行时节点访问 | 现有架构可复用 |
| Three.js `InstancedMesh` / LOD | 重复资产和距离细节 | 现有架构可复用，不能替代手工布局 |
| Playwright + Chrome | 同机位截图、交互和资源加载证据 | 用于验收，不代表真实移动设备性能 |

工具合规要求：每个工具版本固定在 manifest；工具许可证与美术资产许可证分开记录。开源导出器的许可证不授予模型、纹理或场景的使用权。

## 5. 必须由环境美术师完成的部分

以下工作不能靠 GitHub 工具或程序化散布可靠完成：

- 地形侵蚀、海岸线、路径和主视线构图
- 前景/中景/远景的遮挡节奏与视觉焦点
- 植被生态分区、树冠轮廓、密度变化和重复规避
- 岩体、沙滩、水岸的接触细节和材质过渡
- 远景山体、云层和大气透视的统一设计
- 适合实时渲染的材质重建、烘焙和透明贴图审核
- LOD 的人工选择、碰撞代理、可探索范围和遮挡剔除边界
- Blender 基准与浏览器画面之间的逐镜头美术验收

程序化工具可以减少重复劳动，但不能把“随机散布 + 参数调色”视为完整环境制作。

## 6. 最小必要资产包

下一次集成前至少需要一套具有明确网页/游戏分发许可的完整环境包，包含：

1. 可编辑 `.blend` 或等价源工程。
2. 一个连续的局部地形和水岸区域，至少支持一个固定观察点和一段短距离自由移动。
3. 地形、岩体、植被、水体、天空/环境光照和远景构图。
4. glTF/GLB runtime 导出，至少两级 LOD 和独立碰撞代理。
5. PBR 纹理源文件、KTX2/Basis 运行时纹理或可重建的压缩流程。
6. 资产 manifest：作者、来源、许可证、限制、版本、散列、依赖和再分发方式。
7. Blender 基准图、Three.js 同机位图、短时漫游录像和性能采样。
8. 明确的目标画质档位、加载分区、最大纹理预算和已知限制。

如果缺少其中的源工程、许可证、碰撞/LOD 或同机位浏览器证据，资产只能作为参考，不能进入正式项目。

## 7. 质量档位与性能预算

以下是起始预算，不是对所有设备的保证；验收必须记录硬件、浏览器、分辨率、DPR 和实际帧时间。

| 项目 | Intel 核显低档 | Intel 核显中档 | 未来独显高档 |
| --- | ---: | ---: | ---: |
| 目标分辨率/DPR | 1280×720 / 1.0 | 1440×900 / 1.0 | 1920×1080 / 1.25–1.5 |
| 稳定目标 | 30 FPS | 45–60 FPS | 60 FPS |
| 可见三角形起始预算 | 0.5–1.0M | 1–2.5M | 3–6M，按 LOD 调整 |
| 同屏 draw calls 起始预算 | 100–180 | 180–300 | 300–600 |
| 首屏压缩资源 | 20–40 MB | 40–80 MB | 80–160 MB |
| 单张运行时纹理 | 512–1K | 1K–2K | 2K hero，远景降级 |
| 阴影/后处理 | 关闭或一张低分辨率阴影 | 一张主阴影，少量雾 | 选择性阴影、雾和反射 |

高档不能通过关闭 LOD 或把全部 4K 纹理常驻来实现。低档和中档必须仍然保留地形、海岸线、主焦点和空间关系，只降低细节数量、纹理分辨率、阴影和远景效果。

## 8. 进入正式集成前的验收门槛

- 授权清单逐项覆盖场景、模型、纹理、HDRI、植被、音频和工具依赖。
- 无授权不清晰的文件不进入部署包；“公开下载”不等于可再分发。
- Blender 与 Three.js 同机位画面对比，主要地貌、材质层次、天空和光照方向没有明显退化。
- 能够在局部范围内旋转、移动和返回，且相机不会穿透地形或水体。
- 高、中、低档均完成加载、截图、帧时间和资源大小记录。
- 首屏和分区加载没有固定等待伪装；显示的等待必须对应真实资源状态。
- 通过后才建立独立运行时适配器；不修改 Galaxy、Planet、Memory schema 或浏览器存储。

任何一项失败都应停在资产审查阶段，不能用更多粒子、Bloom、颜色调整或临时几何体掩盖失败。

## 9. 更换渲染引擎的条件

当前没有证据表明 Three.js/R3F 存在根本限制，因此默认继续使用现有架构。只有在以下条件同时满足时才建立 PlayCanvas、Babylon 或其他引擎的独立对照：

1. 已取得同一套合法、可编辑、实时就绪资产。
2. Three.js 版本已按本规范完成材质、LOD、压缩、剔除、碰撞和加载优化。
3. 在同一机位、分辨率、DPR 和硬件上，存在可重复的功能或性能瓶颈，而不是美术资产质量问题。
4. 备选引擎能用相同资产提供可测量的收益，并且不会丢失现有导航、数据和 CRUD 能力。

不因某个 Demo 使用 WebGPU、某台 Intel 核显帧率低，或某个离线渲染效果更漂亮，就迁移正式项目。引擎对照必须先在隔离分支完成，使用相同资产和证据格式。

## 当前缺口

当前缺少的不是更多 Shader 或几何代码，而是一套满足上述许可、实时材质、LOD、碰撞、分区加载和同机位证据要求的完整环境资产，以及能够完成地形构图和实时资产整理的环境美术流程。Seacliff Beach 继续保留为构图参考，R1 继续作为稳定运行基线；两者均不作为下一次正式集成的候选。
