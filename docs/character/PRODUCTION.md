## 2. 推荐制作路径

**推荐：先委托统一角色原画，再用 Blender 完成原创脸、发、服装、绑定、表情与动画；按 VRM1/VRMA 导出。** VRoid Studio 可用于比例和兼容性预演，但复杂狐耳、非对称发束、交领分层服装和袖部权重需要定制，不能把默认预设换色视作最终人物。

| 路径 | 适用内容 | 限制 / 出口 |
| --- | --- | --- |
| VRoid Studio 原型 | 快速验证成年比例、头发大形、基础 VRM 表情和导出 | 基础模板及第三方发型/衣服需逐项核查许可；自定义服装不宜硬塞贴图；导出 VRM 后进入 Blender 精修 |
| Blender + VRM Add-on | 原创建模、发束/狐耳、服装分层、shape keys、蒙皮、collider、动画 | 需熟悉 VRM1 与 MToon；先用一个短动作验证当前插件版本的 VRMA 导出和浏览器重定向，再批量制作 |
| 专业画师/建模师/动画师协作 | 最终外观与自然身体语言 | 原画、模型、动作分里程碑交付；采购必须包含源文件、修改权和浏览器分发权，不能只交截图或视频 |

现有环境能编写控制系统、检验文件、运行浏览器与集成资产；**无法在本轮直接产出专业品质的原画、完整定制模型及精修动画。** 所需资产和验收如下，不能用程序骨骼微调弥补缺失。

## 3. 模型、绑定与材质交付

### 几何与权重

- 输出自包含 `.vrm`，VRM 1.0 / glTF 2 binary；纹理内嵌、无外部 URI；另交完整 `.blend`、贴图源稿和导出说明。
- 米为单位，T-pose 与 humanoid 映射正确、左右骨命名一致；记录 DCC 到 VRM 到应用演员局部坐标的轴转换。不能把 Blender Z-up 的坐标直接当 Three.js Y-up；用脚底原点、前方标记和掌心局部轴实测。
- 标定 head、neck、chest、hips、上/下臂、手、五指、上/下腿、脚/脚趾；标准 humanoid 之外独立命名 `foxEar.L/R` 与次级耳尖、发束和衣片骨。
- 肩、腋、肘、腕、髋、膝处保留足够边线。蒙皮审核包含举臂、手臂跨身、肘弯约 120°、掌心翻转、转身、屈膝、脚步与托球姿态；不能只有 T-pose 好看。
- 袖片长度和刚度应支持手掌外露，长发有肩背空间，衣摆不拖地；碰撞无法完全消除的部位优先改版型/权重/动画，不叠加无限 collider。
- 单独标定左右 palm socket：局部位置、朝向、允许球半径、手臂可达区、肩肘 pole 方向；不得继承样本偏移而不检查。

### 表情与视线

基础 `blink`、`blinkLeft`、`blinkRight`、`happy`、`relaxed`、`surprised` 与 VRM 预设保持兼容。六种角色表情按独立设计映射为 `uom_calm`、`uom_curious`、`uom_focused`、`uom_joy`、`uom_surprise_soft`、`uom_warm` 自定义通道；通道可由多组眉/眼睑/脸颊/嘴 morph 组合。实际名称和权重写进模型 manifest，缺失必须报出而非静默当作已实现。

基础眼球采用 bone LookAt。保留眼球/眼睑协同，限制视线范围避免露出眼球边缘。每种表情都检查 0、0.5、1 权重及与双/单眼 blink 的组合；决定并记录 `overrideBlink`、`overrideLookAt`、`overrideMouth` 策略。嘴角微笑不能让闭眼权重固定为 1，惊喜不拉穿眼睑。情绪只由明确交互事件调度，不推断私人记忆的悲喜。

狐耳根部主动表演用额外骨轨道或专用 morph；耳尖可少量物理跟随。**同一骨不能同时由完整主动动画和 spring solver 写入。** 不用普通眼部表情名字暗中驱动所有耳动。

### SpringBone 与材质

- 发束按长度与固定部位分组，刘海、侧发、后发不是同一刚度；编发更稳定。头、颈、肩、胸背、手臂与髋腿设置少量合理 collider，测试转头、抬手和 180° 转身。
- 衣片可用 spring bone 作轻量次级动态；它不是全布料、自碰撞或可靠的多层袖布解算器。复杂接触优先烘焙到动画或缩减服装自由度。
- 使用 MToon 1.0，脸部阴影柔和、皮肤保留中间调；衣服哑光、饰件局部反射，描边随屏幕尺寸控制。尽量 opaque/alpha clip，减少长发、袖片、星纹多层 alpha blend 排序问题。
- 在中性光和现有深空光下对照原画。物理重置、暂停恢复、简化模式均需测试；恢复不能让发裙炸开。Reduced-motion 模式冻结/减弱次级动态，必要互动继续可用。

## 4. 动画机制与控制权评估

| 机制 | 应承担的工作 | 限制及接入要求 |
| --- | --- | --- |
| VRMA | 人形身体、手指、表情、预制视线的完整表演片段 | 当前 3.5.5 类型支持 humanoid 旋转、hips 位移、preset/custom expression、LookAt；不提供任意狐耳/衣片骨的通用 humanoid 轨道 |
| AnimationMixer | 片段播放、循环、一次性动作与衔接 | cross-fade 不会自动保证脚不滑/手不漂；需兼容接续姿态、轨道分组和接触约束；不靠 warp 任意加速表演 |
| IK | 片段之后的小范围掌心/脚底修正 | 限制可达区、关节方向和权重；超限选转步/换构图，不能拉长手臂或替代整个伸手表演 |
| LookAt | 当前真实星球、球体与用户方向跟随 | 动作中明确 authored gaze 与 live target 的所有权及交接；别同时让 VRMA lookAt track 和实时 target 互相覆盖 |
| Expression | 六情绪过渡、眨眼、眼皮/嘴部协调 | 情绪曲线应人工制作；运行时做强度、短暂停顿与中断混合，检查 override 与同时激活权重 |
| SpringBone | 已有身体动作之后的发/衣/耳尖次级反应 | 不代替主动转耳或服装关键接触；不同时播放烘焙摆动又在同一链做完整物理 |

狐耳/服装额外轨道建议交付**同版模型专用 glTF 动画片段 + 节点映射表**，或能表达相应形变的自定义 expression track；VRMA 负责可迁移人形部分。当前 lab 只导入标准 VRMA，**尚未实现该额外轨道加载与混合适配器**。模型专用片段必须绑定模型版本与节点映射，不能承诺跨模型通用。

设计中的每帧顺序：采样主动画 → 小范围目标修正/IK → 规范化骨架到实际骨架同步 → 表情/视线与约束按声明的控制权更新 → spring bones → 更新世界矩阵 → 读取 palm socket 并更新球。落地时必须核查 three-vrm 的实际 update 顺序；不能盲目在 `vrm.update()` 前后重复运行各 manager，或在 normalized/raw 两套骨架混写。此顺序为集成设计，不声称现有控制器已完成该层次。

每条轨道指定单一主写入者：身体由 clip 控制；目标微调由受限修正层控制；眨眼由表情层统一合成；耳根由主动轨道，耳尖由物理。Three.js AnimationMixer 不会自动生成业务需要的骨骼遮罩，需显式分轨或构造 mask；additive 使用前必须统一参考姿态，不能把两个绝对姿态简单相加。

## 5. 标准资产接口提案

沿用现有 `LabActorAsset` 的来源、状态和标定概念，后续增加独立角色包 manifest；**本轮不改运行时接口**。最少包含：

| 字段组 | 必填内容 |
| --- | --- |
| 身份与版本 | characterId、assetVersion、model SHA-256、VRM 版本、审核状态（draft/review/approved） |
| 来源 | 作者、每个外部素材来源、许可、合同/授权记录位置、署名文本、可分发范围 |
| 模型标定 | 实测身高、轴转换、绑定姿态、左右掌心矩阵、球半径范围、视线极限 |
| 表情映射 | 六情绪及 blink 的实际名称、强度区间、互斥/override 规则、缺失处理 |
| 动作 | clipId、文件/散列、duration、loop、兼容模型版本、起止姿态、接地足、层与轨道所有权、淡入淡出 |
| 事件 | `point_ready`、`palm_ready`、`release_ready` 等片段时间点；实际 camera/orb 到达独立来自场景，不放在固定帧假定完成 |
| 额外骨与物理 | 耳/发/服装映射、主动/物理所有权、collider 和 reduced-motion 配置 |
| 质量 | 纹理/面数/材质预算、LOD 版本、已审核视频和已知缺陷 |

事件表与动画文件必须同版并校验标记时间不越界，轨道/表情缺失要明确失败。加载最终包后先做一段短动作往返验证，再进入完整三段；不以文件扩展名存在作为兼容通过。

## 8. 预算、性能与验收关卡

初始目标：桌面角色约 50k–75k 三角形、手机 LOD 约 25k–40k；角色 draw calls 尽量不超过 10–12，基础纹理以 2K 为主（脸可单独 2K），首个模型压缩传输目标约 15 MB 内。预算可随原画调整，不能为追数字直接损伤脸和手。12 张 2K RGBA 纹理含 mipmaps 约占 256 MiB，磁盘压缩小不代表 GPU 内存小，应尽量合图并减少贴图通道。

下一轮用相同场景比较「无角色 / 待机 / 旅行 / 托球」：记录实际 GPU/浏览器、视口/DPR、冷/热加载、帧时间 p50/p95、draw calls/triangles、texture 内存估计及连续 10 分钟变化。目标桌面 60 fps、手机 30 fps，p95 分别参考 20 ms/40 ms；均为待测目标，不承诺新模型已经达到。真实手机必须实测，不能用桌面缩窄窗口代替。超过预算先减透明层/材质/物理链和 DPR，脸和手的表演优先保留。

| 关卡 | 进入条件 / 交付 | 通过标准 |
| --- | --- | --- |
| G1 概念 | 三视图、六表情、细节与效果图 | 用户认可统一原创成年狐灵形象；正侧背可建模，脸部与小尺寸轮廓可读 |
| G2 模型 | 中性光转台、六表情、极限姿势/权重与物理录像 | 不用氛围光藏瑕疵；脸/手一致，袖肘/发肩/裙腿无明显穿插；授权齐备 |
| G3 表演 | 三段分镜与预演，再精修片段 | 眼神、表情、身体有因果顺序；准备/缓冲/停顿/恢复完整，连续待机不机械 |
| G4 实验运行 | 最终候选资产在 `/guide-lab` 的 A/B/C 逐段无剪辑录像与近景 | 真实相机/记忆 ID/掌心联动、取消和不同方向正常；实际视觉审核通过，另附性能报告 |
| G5 正式集成 | 用户认可 G4 后才开始 | 原导航与存储回归、跨页状态、隐藏/恢复与 reduced-motion 验证；不自动合并 |

本轮完成的是进入 G1 前的制作简报。G1–G5 尚未通过。轻量 VRM/VRMA 路线可实现所需表现，但自然度取决于原画、模型权重和动画师制作质量；全布料碰撞、任意方向毫无穿插及电影级效果不能从现有技术样机推导出来。
